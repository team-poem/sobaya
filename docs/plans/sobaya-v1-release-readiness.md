# Sobaya v1 출시 준비 검증

2026-10-06 기준 기록입니다. PR #7·#8은 병합됐으며 병합한 `main`은
`2d425116ce3649dae8daee1a4848fc28a3b34647`입니다. 공개 릴리스는 여전히
`v0.9.0`입니다. 아래 로컬 후보의 태그·파일은 GitHub에 게시하지 않았습니다.

## 로컬 배포 후보

별도 임시 clone에서 호환성 수정 커밋
`8ce4f1d28aaf20c1284cc10c726704e73469a78e`에만 `v1.0.0-rc.1` 태그를 붙여 패키징했습니다.

소비 디렉터리는 이 단계에서 비어 있으며 앱 실행 검증과는 구별합니다.
같은 macOS 생성 파일을 네트워크가 차단된 Linux 환경으로 옮겨 독립 설치와

빈 소비 디렉터리는 유지됐습니다. 운영체제별 빌드 결과의 바이트 일치 검증은 아닙니다.

## 플랫폼 검증과 호환성 수정

기존 환경과 분리한 Linux/arm64 VM·컨테이너에서 병합 커밋의 승인된 설치
테스트를 수정 없이 실행했습니다. Bash 5.2.15, jq 1.6, Git 2.39.5,
Node 22.23.3, Go 1.26.3, Vitest 3.2.4, util-linux `flock` 2.38.1을
사용했고 `shlock`은 없었습니다. 컨테이너는 일반 사용자·네트워크 차단 상태입니다.

열두 항목 중 정상 정책을 읽는 7·8·10·11번이 실패했습니다. jq 1.6에서
`"fixture" | contains("\u0000")`가 `true`를 반환해 정상 문자열까지 거부하는
문제였으며 `flock`과는 무관했습니다. 해당 정책 검사 함수는 이전 배포 준비
커밋에서도 동일했습니다. 검사 구현을 문자열의 코드 포인트 배열에서 0의
존재를 확인하도록 바꿨습니다. 비어 있거나 공백뿐인 문자열, 널 문자가 포함된
문자열, 문자열이 아닌 값은 계속 거부합니다. 승인 테스트는 바꾸지 않았습니다.

수정 커밋 `8ce4f1d28aaf20c1284cc10c726704e73469a78e`의 전체
`tests/run.sh`가 Linux와 macOS 모두 종료 코드 0으로 통과했습니다. 계약 검사 38개,
실행기 27개, 도구 67개, 설정 4개, 패키징 4개, 설치 흐름 12개와
next-entry·Go probe·원문 gate 회귀 검사를 포함합니다. Linux 검증용 VM은
중지했으며 기존 환경과 기본 Docker context는 유지했습니다.

재검증에서는 승인 테스트 원문 확인에서 두 번째 문제가 드러났습니다. jq 1.6이
표준 입력의 마지막 널 문자를 제거해 Git 파일 목록과 명령 인자의 마지막 항목을
잃었습니다. 세 입력 경계에 버릴 마지막 레코드를 추가해 마지막 파일·빈 인자를
보존하고, 생산 명령의 실패도 전달하도록 수정했습니다. `--rawfile`로 읽는 별도
입력은 원문을 보존하므로 수정하지 않았습니다.

독립 리뷰에서는 줄바꿈을 포함한 기존 fixture 경로가 정규식에서 누락되는
별도 문제도 재현했습니다. 경로의 줄바꿈까지 읽도록 수정해 원래 보호 기준대로
변조를 거부합니다. 탭·유니코드 경로와 파일 권한도 보존하는지 확인했습니다.

또한 Node 22의 기본 TAP 출력은 오류 이름과 메시지를 분리해 출력했습니다.
이 때문에 존재하지 않는 심볼을 승인 없이 일반 RED로 분류하던 기존 문제를
발견했습니다. Node 초안 probe에 `spec` 출력 형식을 명시해 Node 22·26의
판정을 맞췄습니다. 명시한 새 심볼만 RED로 허용하고 구문·의존성 오류와 건너뛴
테스트는 계속 오류로 판정합니다. 전체 승인 테스트 실행의 TAP 해석은 유지합니다.

## 실제 v0.9 왕복 탐색

실제 `v0.9.0` 커밋 `e789ce4eb4ce70109474eddd83bcce2f0481ed16`과
`f8d9563e917773528f45097133ed8e48dbec6151`의 설치형 실행기를 비교했습니다.
후자는 병합 커밋과 트리 내용이 같습니다. 프로젝트 모드에서 임시 앱·실제 Git/Node·결정적인 셸
작업자를 사용했으며 실제 소비 앱의 승인을 만들거나 유료 모델을 호출하지 않았습니다.
아래는 탐색 결과이며 새로 승인된 호환성 테스트 기준은 아닙니다. 종속 모드의
v0.9 왕복과 연결 워크트리 복귀는 이번 탐색에서 실행하지 않았습니다. v0.9로
돌아가는 단계는 원래 소스 명령을 사용했으며 `bump --version 0.9.0`이 아닙니다.
v0.9에는 설치형 CLI가 없어 새 설치기의 대상 버전으로 사용할 수 없습니다.

| 경우 | 관찰 결과 |
|---|---|
| v0.9에서 완료한 앱 → 설치형 v1 → v0.9 | 원래 훅 설정을 수동 복원한 조건에서 성공. 승인 기준·`state.json`·`usage.jsonl` 바이트와 호출 수 2회 보존 |
| v0.9에서 중단한 항목 → v1에서 `--resume` | 보호 스냅샷 불일치로 거부. 상태·사용량 바이트와 호출 수 보존. v0.9로 복원해 재개·완료 가능 |
| v1에서 중단한 항목 → v0.9에서 `--resume` | 같은 이유로 거부. v1에서 항목을 끝낸 다음 v0.9에서 최종 리뷰·완료 가능 |
| v0.9의 관리 훅이 있는 앱에 v1 연결 | 원래 훅 보존으로 이전 실행기와 설치형 실행기의 린트가 각각 한 번 실행됨 |

설치형 v1의 활성 항목 스냅샷은 작업 공간의 `sobaya.json`·`sobaya.lock`까지
보호합니다. v0.9에는 이 경로가 없어 상태 형식 번호가 둘 다 1이어도 진행 중인
항목을 다른 실행기로 곧바로 넘길 수 없습니다. 스냅샷을 지우거나 다시 승인하는
방식으로 오류를 우회하지 않습니다. 시작한 실행기에서 항목을 마친 뒤 전환해야
하며, 현재 `init`은 중단 상태의 연결 자체를 선제적으로 거부하지는 않습니다.

현재 자동 해제·복귀 명령은 없습니다. 탐색에서는 원래 로컬 `core.hooksPath`가
없던 앱에서 v1이 추가한 해당 설정만 제거해 원래 Git 설정과 훅 동작이 정확히
복원되는 것을 확인했습니다. 이 명령을 기존 사용자 설정이나 연결 워크트리가
있는 저장소에 일괄 적용하면 안 됩니다. 실제 도입에서는 원래 설정의 범위와
값을 보존한 복귀 절차, 이전 관리 훅의 중복 실행 해결을 함께 검토해야 합니다.

## 첫 소비 저장소 도입

첫 PR은 **도입·이전 PR**, 이후 버전 변경은 **bump PR**로 구분합니다.
확인한 후보는 [Poem 협업 하네스 템플릿](https://github.com/team-poem/poem-collaboration-harness-template)의
`3db86615db7d621b6148532c2cd8ea67f9d09147`입니다. 실제 첫 지원 대상 선택과
`cloud-native-go`의 정확한 주소는 아직 확인하지 않았습니다.

Poem의 현재 연결은 소스 clone을 찾고, `git pull`로 갱신하며, 그 안에 어댑터를
추가합니다. 기존 `harness/sobaya.lock`은 연결할 때 생성하는 `repo/sha/checked`
형식이며 현재 main에 커밋돼 있지 않습니다. 새 JSON lock으로 이름만 바꿀 수 없습니다.

도입 PR에서 다룰 구체적인 범위는 다음과 같습니다.

1. 설치·`init`·고정 pin의 `sync`·명시적 `bump` 연결로 전환하고 설치본을 수정하는
   어댑터 주입을 정리합니다.
2. 자체 훅, 상태·digest 검사, 신규 참여·worktree 생성 스크립트가 설치형 훅 연결을
   인식하도록 합니다. 현재 `.githooks`를 강제로 설정하는 동작과 이전 관리 훅을
   함께 실행하는 동작이 새 연결을 깨뜨릴 수 있습니다.
3. Linux에서는 `lock.shell` 파일 존재만으로 실행 중인지 판단하지 않습니다.
   `flock`은 잠금을 해제해도 파일을 남기므로 현재 소비 측 판단은 영구 대기로
   이어질 수 있습니다. worktree별 Git 설정 준비도 필요합니다.
4. upstream 알림을 브랜치 HEAD 비교에서 고정 버전·릴리스 비교로 전환합니다.
5. 기존 협업 테스트를 보존하고 실제 설치본으로 신규 clone·훅·worktree·복귀를
   검증할 테스트 초안을 검토받습니다. 기존 `tests/sobaya.sh`의 가짜 실행기만으로
   실제 소바야 연동 성공을 선언하지 않습니다.

추가로 템플릿 자체 CI는 POSIX 셸 테스트 세 개이며 `AGENTS.md`의 `Test:`는
자리표시자입니다. 현재 소바야의 전체 테스트 해석기는 Go·Node·Vitest를 지원하므로
템플릿 자체를 앱으로 연결해 `bump` 검증까지 하려면 지원할 테스트 명령을 먼저
결정해야 합니다. 템플릿으로 생성한 Go/Node 앱에 소바야를 연결하는 일과는
구별합니다. 템플릿 main에는 `spec.md`·`failed-test.md`도 없으며 기능 브랜치에서
계획을 관리하므로 이를 임의로 만들고 승인해 통과시키지 않습니다.

연결이 갖춰진 다음에는 후보 `bump`로 전체 선언 테스트·포맷·린트를 검증하고,
성공한 `sobaya.json`·`sobaya.lock` 변경을 소비 저장소 PR로 제출합니다. 신규 clone은
리뷰된 lock에 맞춰 `sync` 후 해당 clone의 `init`이 필요합니다.

## 공개 전 남은 단계

- 기존 훅의 중복 실행과 v0.9 복귀 절차에 대한 별도 검토. 진행 중인 항목의
  버전 간 재개는 지원된 것으로 표시하지 않기.
- 수정 PR 검토·병합 후 최종 출시 커밋의 배포 자산 재생성 및 커밋·해시를 담은 릴리스 노트.
- 선택한 소비 저장소에서 실제 `v1.0.0-rc.1` 자산으로 도입 검증 후 안정판 판단.
- 같은 테스트·모델·정책을 사용한 실제 모델 성능·비용 비교. 아직 결과 없음.

정상적인 실패·취소 복구와 전원 장애·SIGKILL 중 두 설정 파일의 원자적 복구는
다릅니다. 후자는 현재 승인된 구현의 보장 범위에 포함되지 않습니다.

## 시험 릴리스 게시 준비

수정 PR을 검토·병합한 뒤 최종 커밋으로 검증용 clone에서 `v1.0.0-rc.1`을
패키징합니다. 현재 문서의 임시 커밋·해시를 그대로 공개 배포 정보로 쓰지 않습니다.
게시할 자산은 패키저가 만든 `sobaya-1.0.0-rc.1.tar.gz`와 매니페스트
`sobaya-1.0.0-rc.1.json`, 같은 커밋의 독립 `install-runtime.sh`입니다.
최종 매니페스트의 커밋·아카이브 해시와 부트스트랩 해시를 릴리스 노트에 기록하고
별도 저장소 설치를 확인한 뒤 GitHub 시험 릴리스로 게시합니다. 게시한 태그를
다른 커밋으로 옮기지 않습니다.

릴리스 노트에는 다음 내용을 포함합니다.

- 작업 공간별 프로젝트·종속 모드와 정확한 버전·커밋·배포 파일 고정.
