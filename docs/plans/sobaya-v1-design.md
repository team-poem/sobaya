# Sobaya v1 프로젝트 모드와 종속 모드 설계

2026-10-02 대화에서 합의한 방향을 보존하는 작업 문서입니다. 배포 방식,
설정 형식과 두 모드의 역할은 확정했습니다. 읽기 전용 설정 검사 명령의 첫 네
테스트 항목은 2026-10-02 사람의 승인을 받아 구현했습니다. 후속 단계의 구체적인
테스트 입력과 기대값은 별도로 검토한 뒤 구현합니다.

## 확정한 방향

- 저장소와 승인·검증 실행기는 하나로 유지합니다.
- 프로젝트 모드는 현재 `apps/`, `brain/` 중심의 작업 방식을 유지합니다.
- 종속 모드는 외부 프로젝트의 디렉터리·지침·훅을 보존하며 소바야를 연결합니다.
- 모드는 설치된 소바야 전체의 전역 설정이 아니라 사용하는 작업 공간의 설정입니다.
- 실행기는 Bash 3.2·jq·Git·표준 Unix 도구를 유지합니다. TOML 파서나 Node
  패키징 의존성을 추가하지 않습니다.
- GitHub Releases와 설치기로 배포합니다. 작업 공간마다 정확한 버전을 고정하며
  실행 중 자동 갱신하지 않습니다. npm 배포는 이번 범위에 포함하지 않습니다.
- 기존 성능과 승인·테스트 보존·전체 검사·독립 리뷰 기준을 유지합니다.

## 고정한 현재 버전

[`v0.9.0`](https://github.com/team-poem/sobaya/releases/tag/v0.9.0)은
`e789ce4eb4ce70109474eddd83bcce2f0481ed16`을 가리킵니다. PR #5의 한국어 검토
주석 방식이 포함됩니다. 게시한 태그를 다른 커밋으로 옮기지 않습니다.

깨끗한 별도 워크트리에서 전체 `tests/run.sh`가 통과했습니다. 실제 Go·Node·
Vitest를 사용했고 유료 모델은 호출하지 않았습니다. 이는 로컬 하네스 검증이며
실제 모델의 성능이나 향후 v1에서의 복귀 호환성을 증명하지 않습니다.

v0.9.0은 Git 체크아웃으로 사용하는 기존 워크스페이스 버전입니다. 자동 생성
소스 압축 파일은 Git 메타데이터가 없어 현재 설치·진단 명령의 실행 환경과
같지 않습니다. v0.9.0에는 새 `sobaya` 명령, 설치기, JSON 설정이 포함되지 않습니다.

## 설정과 lock

작업 공간의 `sobaya.json`은 사람이 정하는 설정입니다.

```json
{
  "config_version": 1,
  "mode": "dependency",
  "runtime": {
    "version": "1.0.0"
  }
}
```

`config_version`은 설정 형식의 버전이고 `runtime.version`은 실행기 출시
버전입니다. `mode`는 `project` 또는 `dependency`입니다. 공유하는 프로젝트의
설정은 Git으로 관리하며 개인 설치 경로는 이 파일에 기록하지 않습니다.

`sobaya.lock`은 도구가 기록할 JSON 파일입니다. 첫 테스트 묶음에서 승인한
필드 구조는 다음과 같습니다. 현재 검사 명령은 이 파일을 읽기만 합니다.

```json
{
  "lock_version": 1,
  "runtime": {
    "version": "1.0.0",
    "commit": "0123456789abcdef0123456789abcdef01234567",
    "sha256": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef"
  }
}
```

위 해시는 설명을 위한 가짜 값입니다. 실제 lock에는 배포 커밋과 배포 파일의
SHA-256을 기록합니다. 설정에는 `v` 접두사 없이 버전을 쓰고 Git 태그에는
`v1.0.0` 같은 이름을 사용합니다. `1.0.0-rc.1` 같은 시험 버전도
허용하며 `main`, `latest`, 버전 범위는 정확한 버전 고정으로 인정하지 않습니다.

설정·lock의 형식과 버전 일치 검사, 원격 커밋의 실제 존재 확인, 내려받은 파일의
해시 검증은 구별합니다. 첫 번째 검사만으로 설치 파일을 신뢰했다고 판단하지
않습니다. 설치 단계에서 신뢰한 릴리스 정보와 아카이브 내용을 검증해야 합니다.

## 설치와 실행의 경계

공통 `sobaya` 명령이 대상 작업 공간의 설정과 lock을 읽고 고정된 실행기를
선택하는 구조를 목표로 합니다. 현재는 `bin/sobaya config check --root PATH`를
구현했습니다. 나머지 명령은 구현 전에 테스트로 확정할 인터페이스 제안입니다.

| 동작 | 제안 명령 | 책임 |
|---|---|---|
| 설정 확인 (구현) | `sobaya config check --root PATH` | 로컬 설정·lock 검사, JSON 결과, 읽기 전용 |
| 최초 연결 | `sobaya init --mode project` 또는 `--mode dependency` | 명시적 모드 선택, 지침·훅 연결 |
| 고정 버전 설치 | `sobaya sync` | lock에 적힌 정확한 실행기를 설치 |
| 버전 변경 | `sobaya bump --version 1.0.0` | 새 릴리스 검증 후 설정·lock 갱신 |
| 개발 실행 | `sobaya loop ...` 등 | 설치된 고정 버전으로 기존 공통 실행기 호출 |

`sync`는 최신 브랜치를 pull하는 명령이 아닙니다. `bump`가 설정·lock을 바꾸고
소비 프로젝트의 검증과 PR을 거쳐 팀의 버전을 변경합니다. 이미 승인된 테스트는
버전 변경에 맞춰 자동으로 다시 승인하거나 수정하지 않습니다.

실행기는 소비 프로젝트의 소스 밖에 버전별로 보관하는 설치 방식을 우선합니다.
일반 실행에는 네트워크 조회·다운로드·추가 워커 호출을 넣지 않습니다. 정확한
캐시 위치와 릴리스 아카이브 구성은 설치 테스트 작성 단계에서 확정합니다.

설치기는 소비 프로젝트의 기존 지침과 훅을 덮어쓰지 않고 명시적으로 연결합니다.
에이전트가 매번 모드를 추측하거나 실행기 소스를 고치는 구조로 만들지 않습니다.
공통 실행기에는 승인·RED·GREEN·무결성 검사·체크포인트·독립 리뷰를 유지하고,
설치·진단·지침 로딩의 차이만 모드에 맞게 연결합니다.

## 복귀와 성능 보존

릴리스 태그만 되돌려서는 복귀가 완성되지 않습니다. 승인 기준, 누적 호출 수,
진행 중인 항목, 검증 기록, 설치된 훅도 호환되어야 합니다. 첫 v1에서는 기존
상태 형식의 호환성을 유지하는 방향을 우선하며 배포 버전과 상태 형식 버전을
구분합니다. 실행 중에는 설치 파일·모드·버전을 교체하지 않습니다.

검증 항목은 다음과 같습니다. 구체적인 테스트는 해당 단계에서 따로 승인받습니다.

- 기존 프로젝트 명령과 승인·검증 결과가 계속 동작합니다.
- 프로젝트별 모드와 버전이 서로 영향을 주지 않습니다.
- `0.9 → 1.0 → 0.9` 왕복 시 승인·누적 한도·진행 상태가 보존됩니다.
- 버전 변경 실패와 취소 시 이전 설치·설정·lock으로 실행할 수 있습니다.
- 항목별 네트워크 조회와 워커 호출 수가 증가하지 않습니다.
- 같은 테스트·모델·정책에서 실행 시간, 토큰, 성공 여부를 비교합니다. 결정적인
  테스트 대역으로 측정하는 실행기 비용과 실제 모델의 비용·품질은 따로 기록합니다.

성능 수치는 아직 측정하지 않았습니다. 회귀 허용 수치를 임의로 정하지 않으며,
v0.9 측정 기준과 비교 결과를 제시해 출시 여부를 판단합니다. 검증을 줄여 속도를
맞추거나 새로운 실패를 통과로 바꾸지 않습니다.

1. 완료: 현재 `main` 검증 및 v0.9.0 릴리스 고정.
2. 완료: 읽기 전용 설정·lock 검사 테스트와 한국어 검토본을 사람에게 승인받음.
3. 완료: 승인된 네 항목의 설정 검사 구현 및 전체 스위트 검증.
4. 다음: [릴리스 묶음과 실제 커밋·해시 생성 테스트 초안](sobaya-v1-release-review.md).
   최초 연결이 진짜 배포 정보를 lock에 기록할 수 있도록 먼저 준비합니다.
5. 이어서: 검증한 배포 파일 설치, 모드별 최초 연결과 훅·지침 공존, 고정 실행·bump와 실패 복구 검증.
6. 출시 전: 두 모드, 기존 명령, 왕복 복귀, 성능 비교와 독립 리뷰.
7. `v1.0.0-rc.1` 소비 프로젝트 시험 후 v1.0.0 출시.

협업 하네스의 기존 [이슈 #4](https://github.com/team-poem/sobaya/issues/4)는
참고 자료입니다. 승인 기준의 내용 해시화, 브랜치별 상태, plan/spec 경로 변경을
이번 배포 구조 변경에 자동으로 포함하지 않습니다. 협업 하네스의 현재 lock은
기록과 차이 알림에 쓰이고 `sync`는 최신 브랜치를 pull하므로, 소바야의 고정 버전
연결 기능이 준비된 뒤 소비 측 변경을 별도로 검증해야 합니다.

`cloud-native-go`의 정확한 저장소 주소는 아직 확인되지 않았습니다. 공통 기능
설계는 진행하며 해당 프로젝트의 연동 검증은 주소 확인 뒤 추가합니다.
