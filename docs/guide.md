# 소바야 사용 가이드

소바야는 **시나리오 목록 → 테스트 하나 → RED → GREEN → 필요한 리팩터링 →
다음 선택**으로 진행합니다. 사람은 제품 의도를 정하고 에이전트는 그 범위에서
테스트와 구현을 발전시킵니다. 테스트마다 별도 승인이나 필수 독립 리뷰를 받는
절차는 없어졌습니다.

## 준비

앱은 `apps/<name>`의 독립 Git 저장소입니다. `tdd-set/bin/install.sh APP`으로
없는 계약·템플릿·Git 훅을 준비합니다. 기존 사용자 훅과 파일은 보존됩니다.
사람은 `spec.md`에 원하는 결과를 적고, 앱 `AGENTS.md`에는 실제 전체 테스트,
포맷·린트 명령을 적습니다. 에이전트가 명세를 임의로 고치지는 않습니다.

```sh
bash scripts/setup.sh .
tdd-set/bin/install.sh apps/example
tdd-set/bin/doctor.sh apps/example
```

`doctor.sh`는 실행 도구와 로컬 설정을 확인하며 유료 모델을 호출하지 않습니다.

## 테스트 하나씩 진행하기

`failed-test.md`에 먼저 행동 시나리오를 문장으로 적습니다.

```md
- [ ] addPositive — 양수 두 개를 더한다
- [ ] addZero — 0을 더한다
```

다음에 확인할 테스트 하나만 구체화합니다. 앱 테스트 파일에서 직접 TDD를 수행할
수도 있고, [런타임 예시](../tdd-set/README.md#scenario-list-and-the-next-test)처럼
현재 항목에 코드와 헤더를 붙여 `step.sh`를 사용할 수도 있습니다.
미래 테스트를 전부 코드로 작성하지 않습니다.

```sh
tdd-set/bin/next.sh apps/example
tdd-set/bin/step.sh apps/example
tdd-set/bin/status.sh apps/example
```

`step.sh`는 현재 테스트를 넣고 실제 실패 원인을 확인한 뒤 구현을 위임합니다.
전체 테스트와 포맷·린트가 통과하면 항목을 체크하고 동작 변경을 커밋합니다.
현재 후보를 미리 커밋하거나 코드 승인을 받을 필요는 없습니다. 단, 이 도구가
다른 사람의 변경을 함께 커밋하지 않도록 플랜 외 기존 변경은 먼저 정리하거나
별도 작업 공간으로 분리합니다.

이미 통과하는 후보는 `ALREADY GREEN`으로 기록하고 구현을 생략합니다.
Go의 새 API에 필요한 미정의 심볼은 기존 스위트가 통과한 뒤 제한적으로 RED로
인정합니다. 문법 오류·잘못된 import·없는 의존성은 구현 성공의 근거가 아닙니다.

## GREEN에서 정리하고 배우기

테스트가 통과한 뒤 현재 코드를 더 이해하거나 바꾸기 쉽게 할 수 있는지 봅니다.
필요하면 소스와 테스트를 함께 리팩터링하고, 작은 변경마다 전체 테스트를
실행합니다. 테스트가 참조하는 이름도 동작과 검증 의미를 유지하며 바꿀 수 있습니다.
동작 변경과 구조 변경은 별도 커밋으로 남깁니다.

```sh
tdd-set/bin/gate.sh apps/example
# 확인한 구조 변경은 refactor: 커밋으로 남깁니다.
```

`gate.sh`는 커밋 전의 정리도 검사합니다. 검사 도중 코드나 Git 상태가 바뀌면
통과로 인정하지 않습니다. 이후 새로운 승인이나 리뷰 없이 다음 테스트를 선택합니다.
발견한 사례는 목록에 추가하고 미래 시나리오는 분리·재정렬·수정할 수 있습니다.
`loop.sh`도 한 테스트 뒤에 돌아오며, 다음 선택은 오케스트레이터가 합니다.

테스트 자체가 틀렸다면 의도한 동작에 비춰 원인을 설명하고 수정한 뒤 다시
실패·성공 근거를 확인합니다. 실패를 감추려고 검증을 삭제하거나 기대값을
현재 구현에 맞추지는 않습니다. 제품 기대 동작이 불명확하거나 달라질 때 사람에게
묻고, 일반적인 테스트 선택과 구조 정리에 반복 승인을 요구하지 않습니다.

## 기능 사이의 멈춤

실제 사용 결과를 관찰했는지, 테스트로만 확인한 것은 무엇인지, 새로 배운 점과
불확실성이 다음 선택에 어떤 영향을 주는지 돌아봅니다. 구조 정리나 다른 접근이
향후 변경을 쉽게 할지 판단합니다. 유용한 정리나 기록이 없을 수도 있습니다.
이미 맡은 범위는 판단 후 이어가고, 요청하지 않은 새 기능을 자동으로 시작하지 않습니다.
`review.sh APP`는 위험이나 불확실성 때문에 별도 검토가 유용할 때 선택해서 씁니다.

## 기존 묶음 플랜 전환

```sh
tdd-set/bin/migrate.sh apps/example
```

작업 트리가 깨끗하고 실행 중인 항목이 없을 때 사용합니다. 아직 테스트 파일을
만들지 않은 예전 플랜도 전환할 수 있습니다. 기존 플랜과 상태 원본은 앱의
Git 작업 디렉터리 아래 `sobaya/history/<run-id>/`에 보관하고, 플랜에는 시나리오
문장과 체크 상태를 남깁니다. 실제 테스트 파일과 기존 실행 기록·누적 호출 수는
보존됩니다. 이 변환 자체가 코드의 GREEN을 증명하지는 않습니다.

이후 아직 하지 않은 시나리오 중 하나를 선택해 현재 이해에 맞는 테스트를
작성합니다. `approve.sh`, 추가·대체 승인 옵션, 중간 체크포인트 리뷰 옵션은
폐기되어 안내 오류를 반환합니다. 소바야 업데이트만으로 앱 전체를 일괄 전환하지는
않습니다. 앱의 독자적인 제품 요구사항은 계속 존중합니다.

## 실패와 복구

실패한 명령과 파일 변경을 보존하고 원인부터 진단합니다. 같은 구현을 이어가려면
`step.sh APP --resume`을 사용합니다. 테스트 오류를 고쳐 새로 시작해야 한다면
`restart.sh APP`으로 현재 시도의 증거를 보관합니다. 이 명령은 파일을 지우거나
호출 예산을 초기화하지 않습니다. 수정 내용을 정리해 일관된 시작점을 만들고,
수정한 테스트를 다시 구체화해 현재의 실패·성공 근거를 확인합니다. 이미 통과하면
그 사실을 기록하며 억지로 RED를 만들지 않습니다.

예전 실행 중 항목이 남아 있다면 같은 방식으로 증거를 보관하고 변경을 진단한 뒤
정리된 상태에서 `migrate.sh`를 실행합니다. 자동 stash/reset이나 숨은 모델 변경은
없습니다. `usage.sh summary APP [RUN_ID]`로 과거 사용량도 확인할 수 있습니다.

## 선택적인 테스트 설명 문서

테스트의 설계를 자세히 함께 검토할 필요가 있으면
`tdd-set/bin/review-view.sh SOURCE NOTES_JSON OUTPUT.md`로 전체 원본과
한국어 설계 근거를 담은 별도 문서를 만들 수 있습니다.
[입력 형식](../tdd-set/skills/tdd/references/human-review.md)에 따라 원본 일치와
줄 범위 누락을 검사합니다. 설명의 정확성과 필요한 파일 목록은 직접 확인합니다.
이 문서는 테스트마다 승인받거나 이후 코드를 고정하는 절차는 아닙니다.
설치된 런타임의 연결·버전 변경은 [설치 안내](installed-runtime.md)를 참고하세요.
