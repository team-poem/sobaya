# Sobaya 사용 가이드

핵심 흐름은 **사람의 명세 → 테스트 초안 → 사람의 승인 → 항목별 구현과 검증 →
최종 게이트**입니다. 에이전트가 테스트를 제안할 수 있지만 승인 주체는 사람입니다.

## 앱 준비와 승인

워크스페이스 루트에서 다음 명령을 실행합니다.

```sh
tdd-set/bin/install.sh apps/example
```

앱은 자체 Git 저장소여야 합니다. `AGENTS.md`의 실제 테스트·포맷·린트 명령을
설정하고, 사람이 `spec.md`의 목표와 제약을 적습니다. `failed-test.md`에는
이름이 있는 체크박스와 완전한 테스트 코드 블록을 둡니다. Node 테스트는 섹션
헤더에 `// file:` 대상·import·공유 상수를 함께 명시합니다.

에이전트에게 테스트 초안과 probe를 요청할 수 있습니다. RED라는 결과만으로
기대값이 옳아지는 것은 아닙니다. 사람이 정상 경로·경계·실패 경로와 필요한
헬퍼를 검토해야 합니다. 검토한 입력을 커밋한 뒤 승인 기준을 기록합니다.

```sh
tdd-set/bin/approve.sh apps/example
tdd-set/bin/doctor.sh apps/example
```

에이전트가 명령을 대신 실행하는 경우에도 정확히 그 입력에 대한 사람의 승인이
먼저 있어야 합니다. 이미 받은 승인을 반복해서 묻지는 않습니다. 파일을 바꿨다면
기존 승인으로 간주하지 않습니다.

## 구현과 검증

```sh
tdd-set/bin/next.sh apps/example
tdd-set/bin/step.sh apps/example
# 또는 남은 항목을 순서대로 진행
tdd-set/bin/loop.sh apps/example 20
tdd-set/bin/status.sh apps/example
tdd-set/bin/gate.sh apps/example
```

하네스가 승인한 테스트 하나를 그대로 추가하고 RED를 관찰합니다. 워커는 필요한
소스 구현만 합니다. 테스트·플랜·검증 명령을 수정하거나 커밋하지 않습니다.
하네스는 보호한 파일과 Git 상태를 확인하고 전체 스위트와 필수 검사를 통과한
경우에만 체크박스를 갱신하고 행위 변경을 커밋합니다. 통과 보고만 믿고 다음
항목으로 넘어가지 않습니다. 최종 게이트 뒤에는 새 컨텍스트의 독립 리뷰가
실행됩니다. 리뷰는 해당 HEAD에 연결되며, 지적 사항이나 실행 실패가 있으면
완료가 보류됩니다. `step.sh`만 사용했다면 `review.sh`로 리뷰를 수행합니다.

전체 테스트는 검증 시점의 기본 요구사항입니다. 개발 중 특정 테스트만 실행한
결과가 이를 대체하지는 않습니다. 별도 구조 리팩터링을 요청할 때는 green에서
작게 변경하고 재검증하며 행위 변경과 커밋을 나눕니다.

## 모델 선택과 실행 한도

기본 워커는 Astra입니다. 다른 모델·제공자를 쓰려면 워커 정책을 작성하고
`step.sh` 또는 `loop.sh`에 `--policy <경로>`로 지정합니다. 형식은
[런타임 레퍼런스](../tdd-set/README.md#worker-policy)에 있습니다.

정책은 정확한 허용 워커, 선택 모드, 최대 호출 수와 시간을 명시합니다.
`selected`는 선택한 워커를 유지합니다. `quality`와 `economy`도 명시된 정책
범위에서만 동작하며 설정 없는 상위 모델 전환을 허용하지 않습니다. 구성된
전환도 진단을 포함한 handoff가 있어야 합니다. 모델이 달라도 승인·테스트·
게이트 기준은 같습니다.

최종 리뷰 호출도 `max_calls`에 포함되므로 그 여유를 남깁니다.

새 세션이 기본입니다. 검증 경계와 세션 수는 별개이지만, 현재 세션 재사용이
구현되었다고 가정하지 않습니다. 하네스 테스트에서는 유료 모델을 호출하지
않습니다. 실제 실행 전 정책과 호출·시간 한도를 확인하세요.

## 실패·새 결함·테스트 변경

실패하면 `status.sh`와 실제 출력으로 원인을 확인합니다. 실행 환경 오류,
구현 실패, 보호 파일 변경, 잘못된 기대값을 구분합니다. 같은 작업을 맹목적으로
재시도하거나 모델만 바꾸지 않습니다. 하네스와 작업 파일을 실행 중에 고치지도
않습니다. 남은 변경과 진단을 확인한 뒤 명시적인 `--resume`으로 재개합니다.
자동 stash나 reset을 가정하지 않습니다.

승인된 테스트가 틀렸거나 새 결함의 회귀 테스트가 필요하면 별도 초안을
제시합니다. 기존 승인 플랜을 고쳐서 루프를 통과시키지 않습니다. 사람이 변경을
검토하고 명시적으로 승인한 뒤 커밋하고 기준을 교체합니다.

```sh
tdd-set/bin/approve.sh apps/example --replace
```

이 명령은 자동 복구 수단이 아닙니다. 사람의 승인이 필요한 작업은 구체적인
수정안을 준비한 상태로 요청하고, 영향 없는 승인된 작업은 계속 진행합니다.

## 협업과 메모리

관련 brain 노트와 저장소 상태부터 읽습니다. 단순 작업은 직접 진행하고,
독립적으로 진행할 수 있는 탐색·구현이나 중요한 변경의 독립 리뷰에만
서브에이전트를 사용합니다. 파일 수만으로 위임하지 않습니다. 체크아웃당
작성자는 한 명이며, 병렬 변경은 별도 워크트리를 사용하고 순서대로 통합합니다.

공통 지식은 `brain/`, 앱 설계와 앱 플랜은 앱 저장소에 둡니다. 오래 걸리는
작업은 진행 상황을 남기고, 완료 후 `reflect`로 지속적으로 유용한 학습만
기록합니다. 생성되는 `brain/index.md`는 직접 편집하지 않습니다. `python3 scripts/brain-index.py .`로 인덱스를 갱신하고 `--check`로
동기화 여부를 확인할 수 있습니다. 호스트 훅 설치만 믿지 말고 필요한
인덱스를 직접 읽으며 실제 연결 상태는 진단 명령과 실행 증거로 확인합니다.


## 공통 훅 설치와 실행 경계

최초 한 번 `python3 scripts/setup.py .`로 루트 Git 훅을 연결합니다.
`python3 scripts/setup.py . --check --app apps/<name>`은 루트와 앱 훅이
실제로 이 하네스를 가리키는지 확인합니다. 기존 사용자 훅이 있으면 보존하고
충돌을 보고하므로, 기존 동작을 검토하여 통합한 뒤 설치합니다.

`doctor.sh`는 설정과 실행 파일 존재 여부를 확인하며 모델 인증·접근 권한이나
실제 API 호출 성공을 보증하지 않습니다. 지원 테스트 러너는 `go test`,
`node --test`, 로컬 `vitest run`과 이를 감싼 단순 npm 스크립트입니다.
셸 체인이나 npm 전후 실행 훅은 테스트 명령으로 허용하지 않습니다.

이미 GREEN인 승인 항목은 구현 호출을 생략하고 테스트만 검증·커밋합니다.
Go 새 함수가 아직 없으면 기본적으로 빌드 오류입니다. 사람이 명시적으로
`approve.sh APP --allow-go-undefined-red`를 승인하면 기존 스위트의 성공을
먼저 확인한 뒤, 선택한 테스트 파일의 미정의 심볼만 build-red로 기록합니다.
누락된 import·문법·다른 패키지 오류는 계속 거부하며 GREEN은 실제 테스트
실행으로 증명해야 합니다. 준비 도중 환경 오류는 해결 후 `--resume`할 수 있습니다.

`max_calls`는 승인한 기준별 누적 한도이며 재실행으로 초기화되지 않습니다.
중단·시간 초과 시 작업자 프로세스 그룹을 종료한 뒤 쓰기 잠금을 해제합니다.
강제 종료로 살아남은 작업자가 있으면 다음 실행을 차단합니다. 커밋 훅 실패는
검증한 파일이 그대로인 경우 워커를 다시 호출하지 않고 커밋을 재시도할 수 있습니다.
